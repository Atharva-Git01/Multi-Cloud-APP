1. Executive Summary
BBG Cloud App is a multi-cloud file intelligence platform. It takes any file uploaded by the user — image, video, audio, document, or other media — and automatically routes it to the most appropriate free-tier cloud storage provider based on file type, size, and available capacity. The user never manually manages multiple cloud accounts. They sign up once with a single email and password, and BBG creates and manages all cloud accounts on their behalf.
The aggregated free tier across all supported providers gives each user up to 75 GB of completely free, intelligently organised cloud storage — more than any single provider offers alone.
Value Proposition
✦  Single sign-in — one email/password manages everything
✦  Automatic account creation on all selected cloud platforms
✦  Smart routing — right file type goes to the right cloud
✦  Full transparency — see all providers, space, and where each file lives
✦  Up to 75 GB free storage by aggregating multiple platforms
✦  Access all files from one unified app interface
2. Core Concept: Intelligent Multi-Cloud Routing
2.1  The Problem BBG Solves
Free cloud storage is widely available, but fragmented. A user who signs up to Google Drive, OneDrive, MEGA, Box, and pCloud individually would have over 60 GB of free storage — but they would need five separate accounts, five apps, and no way to find files across them. BBG unifies all of this behind a single interface.
2.2  How Routing Works
When a user uploads a file, the Smart Routing Engine analyses three factors in priority order:
File Category — MIME-type determines which cloud is the best semantic fit (e.g. documents to OneDrive, media to Google Drive).
Available Capacity — The engine checks how full each cloud account is. If the preferred cloud is above 85% full, it falls over to the next best provider.
File Size — Large files (>100 MB) are never sent to providers with per-file upload limits (Box free: 250 MB max). Very small files are bundled to avoid request overhead.

If a primary provider's storage is above 85% full:
Engine queries all provider quotas in real time via their respective APIs

If all providers are above 90% full, user is notified with a storage dashboard alert
User can manually choose to move files between providers from within the app

4.2  Routing Algorithm — Pseudocode
route_file(file, user_id) → provider
def route_file(file: UploadedFile, user_id: str) -> ProviderName:
    category = detect_category(file.mime_type)
    quota_map = await fetch_all_quotas(user_id)   # parallel
    primary = CATEGORY_ROUTING_TABLE[category]     # preferred provider
    # Try primary provider first
    if quota_map[primary].free_pct > 15:           # > 15% free remaining
        if not exceeds_file_limit(file, primary):  # e.g. Box 250MB cap
            return primary
    # Fallback: sort remaining providers by free space, pick best
    candidates = sorted(
        [p for p in quota_map if p != primary and quota_map[p].free_pct > 10],
        key=lambda p: quota_map[p].free_gb, reverse=True
    )
    for provider in candidates:
        if not exceeds_file_limit(file, provider):
            return provider
    raise NoStorageAvailableError(user_id)
4.3  Quota Monitoring Service
A background task runs every 15 minutes per active user to refresh quota data and cache it in Redis. This ensures the routing engine always has near-real-time quota information without making live API calls on every upload.
QuotaRefreshWorker — Python async task, Celery Beat or APScheduler
Quota data cached in Redis with 15-minute TTL
Android app polls /api/storage/dashboard every 5 minutes when app is in foreground
Push notification sent when any provider crosses 80% full threshold

5.3  Auto Account Creation — Technical Implementation
5.3.1  Google Drive
Google Drive uses the existing Google OAuth flow. The user signs in with Google during step 3 — this is their primary identity. No separate account creation needed.
5.3.2  Microsoft OneDrive — Auto Account Creation
User's email + BBG-generated password sent to Microsoft account creation API
Microsoft Account creation endpoint: https://signup.live.com/signup
BBG backend automates this via Microsoft's account registration API (requires approved partner access) OR uses a guided WebView that pre-fills the email/password for the user to complete with a single tap
OAuth2 flow via MSAL follows immediately after account creation
Refresh token stored securely in BBG's database per user
5.3.3  MEGA — Auto Account Creation
MEGA API supports programmatic account creation via POST /cs endpoint
Parameters: email (user's BBG email), password (hashed with MEGA's key-derivation)
After creation, MEGA sends a verification email — BBG auto-clicks via email parsing OR guides user through a single email verification tap
Uses megajs SDK on backend for all subsequent operations
5.3.4  Box — Auto Account Creation
Box Individual free accounts can be created via Box's registration API
BBG uses OAuth2 App with Box to authenticate after creation
250 MB per-file limit enforced at routing layer
5.3.5  pCloud — Auto Account Creation
pCloud REST API: POST /userregister with email + password creates free account instantly
No email verification required for free accounts (unlike MEGA)
Immediate OAuth token issuance after registration
5.4  Email Verification Handling Strategy
Verification Strategy
For platforms that require email verification (MEGA, OneDrive):
Option A — Guided Tap (Recommended for v1):
  • BBG sends user a push notification: 'Tap to verify your MEGA account'
  • Opens the verification email in a WebView inside the app
  • User taps Verify — returns to app automatically
Option B — Background Verification (v2 Feature):
  • BBG backend uses IMAP to read the verification email
  • Automatically clicks the verification link server-side
  • Requires user to grant BBG inbox access (risky — deprioritise)
For platforms with no verification (pCloud, Box):
  • Accounts are live immediately — no user action needed

@HiltViewModel
class OnboardingViewModel @Inject constructor(
  private val createAccounts: CreateCloudAccountsUseCase,
  private val getCreationStatus: GetAccountCreationStatusUseCase
) : ViewModel() {
  private val _selectedProviders = MutableStateFlow<Set<CloudProvider>>(setOf(GOOGLE))
  val selectedProviders = _selectedProviders.asStateFlow()
  val totalSelectedGB: StateFlow<Int> = selectedProviders.map { set ->
    set.sumOf { it.freeStorageGB }
  }.stateIn(viewModelScope, SharingStarted.Eagerly, 15)
  fun toggleProvider(provider: CloudProvider) {
    if (provider == GOOGLE) return  // cannot deselect Google
    _selectedProviders.update {
      if (provider in it) it - provider else it + provider
    }
  }
  fun createAccounts(email: String, password: String) {
    viewModelScope.launch {
      createAccounts(email, password, _selectedProviders.value)
        .collect { status -> _creationStatus.value = status }
    }
  }
}

11.2  Provider Service Interface
BaseCloudProvider interface (Python)
class BaseCloudProvider(ABC):
    @abstractmethod
    async def create_account(self, email: str, password: str) -> ProviderAccount:
        """Programmatically create a new account on this provider."""
    @abstractmethod
    async def upload_file(self, file: UploadFile, remote_folder: str,
                          credentials: ProviderCredentials) -> RemoteFile:
        """Upload a file and return its remote path and URL."""
    @abstractmethod
    async def get_quota(self, credentials: ProviderCredentials) -> QuotaInfo:
        """Return used_bytes, total_bytes, free_bytes."""
    @abstractmethod
    async def delete_file(self, remote_id: str,
                          credentials: ProviderCredentials) -> bool:
        """Delete a file from this provider."""
    @abstractmethod
    async def get_share_link(self, remote_id: str,
                             credentials: ProviderCredentials) -> str:
        """Generate a public share URL."""
12. Security & Compliance
12.1  Auto Account Creation Security
Critical Security Rules for Auto Account Creation
1. User email + password are NEVER stored in BBG's database in plaintext.
   They are used once during account creation, then discarded.
   Only OAuth tokens (access + refresh) are persisted — AES-256 encrypted.
2. The user's BBG password is separate from cloud provider passwords.
   BBG generates strong random passwords for each provider account internally.
   Users do not need to know these generated passwords.
3. All OAuth tokens stored in PostgreSQL are encrypted at rest (AES-256).
   Encryption key stored in environment variable / Vault — never in code.
4. Programmatic account creation APIs are called over HTTPS only.
5. MEGA encryption keys are never stored on BBG servers — MEGA is
   end-to-end encrypted and keys are derived client-side.
